# Haddak — API contract

The contract between the mobile app and the FastAPI backend. Both sides are built against this file. Change it here first, then change the code.

- Base path: `/api/v1`
- JSON in and out, `snake_case` field names.
- Errors: `{"detail": "human-readable message"}` with a fitting status code (400, 401, 403, 404, 409, 422).
- Interactive docs are generated by FastAPI at `/docs`.

## Authentication

Supabase Auth issues the login token. The app sends it as `Authorization: Bearer <access_token>`. The backend verifies the token's signature and reads the user id from the `sub` claim. It supports both HS256 with `SUPABASE_JWT_SECRET` and Supabase's JWKS endpoint, chosen by configuration.

"Auth" below means the header is required; a missing or invalid token gives 401.

Admin routes use the header `X-Admin-Key: <ADMIN_API_KEY>` instead.

## Provider statuses and who sees what

A provider can be listed without being verified.

| Status | Public? | Meaning |
|---|---|---|
| `unverified` | yes, `verified: false` | No proof submitted, or the proof was not accepted. |
| `pending` | yes, `verified: false` | Proof submitted, waiting for the founder. |
| `verified` | yes, `verified: true` | The founder checked the proof. This is the badge. |
| `rejected` | no, 404 everywhere public | Fake, abusive or duplicate. |

- Public shapes never contain `status` or `verification_doc_url`. `pending` and `unverified` look identical to the public.
- Search returns verified providers only, unless `include_unverified=true` is sent.
- Verification is a human decision made in the admin page.

## Public endpoints

| Method and path | Purpose |
|---|---|
| `GET /health` | `{"status": "ok"}`. Also checks the database connection; 503 if it is down. |
| `GET /categories` | All categories, ordered by `sort_order`. Flat list; the app builds the tree from `parent_id`. |
| `GET /providers/search` | Radius search. See below. |
| `GET /providers/{id}` | `ProviderDetail`. Optional `lat`, `lng` to get `distance_m`. 404 if unknown or rejected. |
| `GET /providers/by-slug/{slug}` | Same as above, by share code. |
| `GET /providers/{id}/reviews` | `{"items": [Review], "total": n}`. Query: `limit` (default 20, max 50), `offset`. Newest first. `is_mine` is set when a token is sent. |
| `POST /providers/{id}/contact-events` | Body `{"type": "view" \| "whatsapp" \| "call"}`. Returns 204. No login. |
| `POST /providers/{id}/reports` | Flag a bad listing. Body below. Returns 201 `{"id": "uuid"}`. No login. 404 if unknown or rejected. |
| `POST /suggestions` | Suggest a provider who is not on Haddak yet. Body below. Returns 201 `{"id": "uuid"}`. No login. |
| `GET /providers/{id}/stories` | `{"items": [Story]}`: the provider's active stories, newest first. 404 if unknown or rejected. |
| `GET /stories/nearby` | `{"items": [StoryGroup]}`. Query: `lat`, `lng`, `radius_m` (100 to 50000), all required. Active stories of verified providers inside the circle, grouped by provider; the provider with the newest story comes first; at most 30 providers. `distance_m` is set in each provider. |

`GET /providers/{id}` and `GET /providers/by-slug/{slug}` read the login token when one is sent, only to fill `is_following`. A missing or bad token is treated as anonymous.

### `GET /providers/search`

| Query | Type | Rules |
|---|---|---|
| `lat`, `lng` | float | required |
| `radius_m` | int | required, 100 to 50000. App chips: 500, 1000, 5000, 20000 ("city") |
| `category_id` | int | optional; includes child categories |
| `q` | string | optional, 2 to 60 characters; keeps providers whose name contains it (case-insensitive). Works together with `category_id`. |
| `include_unverified` | bool | default `false`: verified providers only. `true`: also `unverified` and `pending` ones (never `rejected`). |
| `max_price` | number | optional (> 0); keeps only providers with a structured price `price_amount <= max_price`. Needs `price_unit`; `price_currency` defaults to `USD`. Providers without a structured price are left out when this is set. |
| `price_unit` | string | `hour`, `visit`, `job`, `item`, `month`; required with `max_price` (422 without it), ignored without it |
| `price_currency` | string | `USD` (default) or `LBP` |
| `open_now` | bool | default `false`; `true` keeps providers whose opening hours say open now (Beirut time). Providers with no hours are left out. |
| `sort` | string | `best` (default, the order below) or `distance` (nearest first; verified still before non-verified) or `price` (cheapest structured price first, then the default order) |
| `limit` | int | default 30, max 100 |
| `offset` | int | default 0 |

Response: `{"items": [ProviderSummary], "total": n}`. Order (`sort=best`): all verified providers before all non-verified ones; inside each group featured first, then weighted rating, then distance (see `SCHEMA.md`). Featured placement only counts for verified providers. `sort=price` compares the amount only (providers without a structured price last), so it is most useful together with `max_price`, which fixes the unit and currency.

### `POST /assist` (assistant, see `AI_ASSISTANT.md`)

No login needed. Rate limit: `ASSIST_DAILY_LIMIT` (default 30) per IP per day, counted only for requests that reach the AI.

Request, either a sentence:

```json
{ "text": "baddé sankari 2arib", "lat": 33.85, "lng": 35.52, "lang": "ar" }
```

or a chosen clarify option (no AI request is made; the settings are searched directly):

```json
{ "understood": { ...Understood... }, "lat": 33.85, "lng": 35.52, "lang": "ar" }
```

`text` 2–300 characters. `lang` (`ar` or `en`, default `en`) picks the language of `summary`. Send exactly one of `text` and `understood` (both or neither is 422). `lat` and `lng` are required.

In the `understood` form every field is optional (defaults: no categories, `radius_m` 1000, `price_currency` `USD`, `open_now` false, `sort` `best`) and is checked again like the AI's answer. `place` is read by its slug only: `{"slug": "jdeideh-metn"}` is enough, and anything else in it (names, coordinates) is ignored. This is what the app sends after the user taps one of `place_options`. A known slug centres the search on that place; an unknown slug is answered like a place we could not find (`place_unknown` = the slug, search near the phone).

`Understood` (what the AI returns, after the backend checks it):

```json
{
  "category_slugs": ["plumber"],            // only slugs that exist; may be empty when q is set
  "q": null,                                // optional name keyword
  "place": null,                            // or {"slug","name_en","name_ar","lat","lng"} after the lookup
  "radius_m": 1000,                         // 500, 1000, 5000 or 20000
  "max_price": null, "price_unit": null, "price_currency": "USD",
  "open_now": false,
  "sort": "best"                            // best | distance | price
}
```

Response:

```json
{
  "kind": "results",        // results | clarify | emergency | off_topic | unavailable
  "understood": { ... } | null,
  "summary": "Plumber · near you · 1 km",   // built from a template, not by the AI
  "results": { "items": [ProviderSummary], "total": 4 } | null,
  "widened": false,         // true when nothing was found and the radius was widened once (1 km → 5 km → 20 km)
  "question": null,         // clarify: {"text": "...", "options": [{"label": "...", "understood": {...}}]}
  "place_options": null,    // two places share the name: [{"slug","name_en","name_ar","district"}]
  "place_unknown": null,    // the place name we could not find; the search used the phone location
  "whatsapp_draft": "مرحبا، لقيتك على حدّك. عندي تسريب مي…" | null
}
```

- `unavailable`: no API key, monthly cap reached, this IP's daily AI allowance used up, or the AI failed. The app then runs a normal name search with the text.
- `emergency`: the app shows its own built-in emergency numbers. `off_topic`: the app shows one fixed polite line.
- The AI request is sent only the sentence and the category list. The phone location never leaves the backend.

Details settled in the backend build:

- `summary` is always a string. For `results` it is the template (category, or the name keyword in quotes · `near you` or `in <place>` · radius · price limit · `open now` · `nearest first` / `cheapest first`, in English or Arabic); for the other kinds a fixed sentence.
- `results`: up to 20 items; `total` counts all. Unverified providers are included, always after every verified one. `distance_m` is measured from the search centre (the place when one was found, otherwise the phone).
- `understood.radius_m` is the radius finally searched. A found place sets it to at least the place's size (Jounieh: 5 km, Hamra: 1 km). Widening: when nothing is found, the next bigger radius is tried (500 → 1000 → 5000 → 20000) until something is found or 20 km was tried; `widened` is then true.
- When no category fits and no name keyword was given, `results` is `{"items": [], "total": 0}` without searching (and the request goes on the founder's "wanted" list).
- `clarify`: `understood` and `results` are `null`; `question.options` has 2 to 4 options, each with a full `understood` whose place (if any) is already looked up. `whatsapp_draft` may be set. The app sends the chosen option's `understood` back.
- `place_options` comes with kind `results`: the search ran near the phone, `understood.place` is `null`, and each option is `{"slug","name_en","name_ar","district"}`. Tapping one sends the `understood` form with `place: {"slug": ...}` (see above).
- `emergency`, `off_topic` and `unavailable`: only `kind` and `summary` are set; everything else is `null` (`widened` false).
- Unknown category slugs from the AI are dropped; at most 3 are kept. `radius_m` is snapped to the nearest of 500, 1000, 5000, 20000. A price limit without a unit is dropped; the currency defaults to `USD`.

### `POST /providers/{id}/reports`

```jsonc
{ "reason": "not_real", "note": "This shop closed years ago." }
```

`reason` is required: one of `wrong_info`, `not_real`, `closed`, `offensive`, `other`. `note` is optional, up to 500 characters. Nothing about the sender is stored (no user id, no IP).

### `POST /suggestions`

Body (only `name` is required):

```jsonc
{ "name": "Abu Ali Tailor", "phone": "+96170123456", "category_id": 3,
  "area_name": "Mazraa", "note": "Best tailor in the area.",
  "lat": 33.8872, "lng": 35.4955 }
```

Limits: `name` 1 to 100 characters, `area_name` up to 100, `note` up to 500; `phone` in the same international format as provider phones. `lat` (-90 to 90) and `lng` (-180 to 180) are optional, but must be sent together: one without the other is 422. An unknown `category_id` is 400. Nothing about the sender is stored (no user id, no IP).

## Auth endpoints

| Method and path | Purpose |
|---|---|
| `GET /providers/{id}/reviews/mine` | My review of this provider as a `Review`, or `null` if I have not written one. 404 if the provider is unknown or rejected. |
| `PUT /providers/{id}/reviews/mine` | Create or update my review. Body `{"rating": 1-5, "comment": "…", "author_name": "…"}`. Returns `Review`. 403 on own profile. |
| `DELETE /providers/{id}/reviews/mine` | Remove my review. 204. |
| `GET /me/provider` | `OwnProvider`, or 404 if the user has no profile. |
| `POST /me/provider` | Create my profile. Body below. Returns 201 `OwnProvider`. `status` is `"pending"` if a `verification_doc_url` was sent, otherwise `"unverified"`; the profile is listed publicly either way. 409 if one exists. |
| `PATCH /me/provider` | Update any of the create fields. Returns `OwnProvider`. Status rules below. |
| `GET /me/provider/stats` | `{"month": "2026-11", "views": 40, "whatsapp": 9, "calls": 3}` for the current month. |
| `POST /me/provider/stories` | Post a story. Body `{"text": "…", "image_url": "https://…"}` (`image_url` optional). Returns 201 `Story`. Rules below. |
| `DELETE /me/provider/stories/{story_id}` | Delete one of my stories. 204; 404 if it is not mine or does not exist. |
| `PUT /me/provider/banner` | Set my banner, replacing the one I had. Body below. Returns `Banner`. |
| `DELETE /me/provider/banner` | Remove my banner. 204, also when there was none. |
| `PUT /providers/{id}/follow` | Follow a provider. 204, also when already following. 404 if unknown or rejected. |
| `DELETE /providers/{id}/follow` | Unfollow. 204, also when not following. 404 if unknown or rejected. |
| `GET /me/following` | `{"items": [ProviderSummary], "total": n}`: providers I follow, most recently followed first. Query: `limit` (default 50, max 100), `offset`. Rejected providers are left out. `distance_m` is null. |
| `GET /me/feed` | `{"items": [StoryGroup]}`: active stories of the verified providers I follow, grouped by provider; newest story first; at most 30 providers. `distance_m` is null. |

Create body:

```jsonc
{ "name": "Ali Tech", "category_id": 3, "description": "…", "price_text": "From $10",
  "price_amount": 10, "price_unit": "job", "price_currency": "USD",
  "phone": "+96170123456", "whatsapp": null,
  "lat": 33.8551, "lng": 35.5102, "area_name": "Haret Hreik",
  "photos": ["https://..."], "verification_doc_url": "…" }
```

Phone numbers must be in international format (`+` and 8 to 15 digits).

`verification_doc_url` is optional. How `PATCH /me/provider` treats it:

- On an `unverified` profile, sending a `verification_doc_url` that is not the one already stored moves it to `pending` (proof waiting for the founder). Sending the same URL again changes nothing, so a declined proof is not queued again by an ordinary edit.
- On a `pending` profile, clearing it with `null` moves the profile back to `unverified`.
- Every other edit keeps the status. A `verified` profile stays verified; a `rejected` profile stays rejected whatever is sent.

Two optional fields can also be sent on create and on update:

- `show_contact_count` (boolean, default `false`): when `true`, the public profile shows `contacts_this_month`.
- `opening_hours` (object or `null`, default `null`): see below. `PATCH` with `null` clears the hours.

- `price_amount` (number > 0, up to 100,000,000, or `null`), `price_unit` (`hour`, `visit`, `job`, `item`, `month`, or `null`) and `price_currency` (`USD` or `LBP`, default `USD`): the structured price that search filters and sorts on. `price_text` stays the free-text description. Amount and unit are set together or both `null`; one without the other is 422, also on `PATCH`, where the check is made against the stored values (sending only a new `price_amount` keeps the stored unit; clearing needs both set to `null`). `price_currency` cannot be `null`.

- `sponsor_hook` (string or `null`, default `null`): a one-sentence pitch, 1 to 80 characters. `null` (or an empty string) clears it. The owner may set it at any time, but the public only receives it while the profile is sponsored (see "Sponsored" below).

### Stories and banners

Only the owner of a `verified` profile may post: 404 without a profile, 403 while the profile is not verified. Deleting your own story or banner is always allowed.

- **Story.** `text` 1 to 280 characters; `image_url` optional (`null` or an empty string means none), must start with `https://`, up to 1000 characters. It is active for 24 hours (`expires_at` = `created_at` + 24 h). At most 5 active stories per provider: a sixth is 409 until one expires or is deleted.
- **Banner.** One per provider; `PUT` replaces the old one. Body:

```jsonc
{ "title": "Back to school offer", "text": "All laptop repairs this week.",
  "discount_percent": 20, "days": 7 }
```

`title` 1 to 60 characters. `text` optional, up to 200 (`null` or an empty string means none). `discount_percent` optional, 1 to 90. `days` optional, 1 to 7, default 7: the banner starts now (`starts_at`) and expires `days` days later.

Expired stories and banners are simply no longer returned; nothing deletes them in the background. If a profile stops being verified, its stories and banner are hidden everywhere public until it is verified again: `has_active_story` is `false`, `banner_title` and `active_banner` are `null`, and its story list is empty.

### Sponsored

"Sponsored" is what users see for the admin's "featured" placement. `sponsored` is `true` when the provider is verified and `featured_until` has not passed; it always equals `featured`, which is kept for older app builds. `sponsor_hook` is `null` unless `sponsored` is `true`. Sponsored providers come first among verified ones in search (the existing featured rule; nothing else about the order changed). There are no payments in the app: the admin sets `featured_until` by hand.

### Opening hours

```jsonc
{ "mon": [["09:00", "13:00"], ["15:00", "19:00"]], "sat": [["10:00", "14:00"]] }
```

- Keys: any of `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun`. Any other key is 422.
- Each day: a list of at most 3 `[open, close]` pairs, 24-hour `"HH:MM"` from `00:00` to `23:59`, with open before close.
- A missing day (or an empty list) means closed that day. `null` for the whole field means "hours not provided".
- No overnight ranges in v1: a range cannot cross midnight (`["22:00", "02:00"]` is 422). `["00:00", "23:59"]` is the longest possible day.
- Times are Lebanon local time. `open_now` is computed in the `Asia/Beirut` timezone: open from the opening minute up to, but not including, the closing minute. It is `null` when `opening_hours` is `null`.

### Status changes (`PATCH /admin/providers/{id}`)

The admin page's buttons all send `status` to this one route:

| Action | Body | Used on |
|---|---|---|
| Verify (Approve) | `{"status": "verified"}` | `pending` or `unverified` |
| Decline proof | `{"status": "unverified"}` | `pending`. The listing stays visible, without the badge. The proof link is kept so the founder can still see what was declined. |
| Reject | `{"status": "rejected"}` | any. Hidden everywhere public. |
| Restore | `{"status": "unverified"}` | `rejected`. Listed again, without the badge. |

The route accepts any of the four statuses and does not check which status the profile had before: the admin is trusted.

### `POST /admin/suggestions/{id}/publish`

Creates a provider with `status: "unverified"`, `source: "suggestion"` and no owner (`claimed: false`), with a share code generated like any other profile's. The suggestion is deleted in the same transaction.

The body is optional. Any field in it overrides the suggestion's value; a field left out or `null` keeps the suggestion's value:

```jsonc
{ "name": "Abu Ali Tailor", "phone": "+96170123456", "category_id": 3,
  "area_name": "Mazraa", "lat": 33.8872, "lng": 35.4955, "description": "…" }
```

- After merging, `name`, `phone`, `category_id`, `area_name`, `lat` and `lng` must all be present; otherwise 422 with `{"detail": "Missing: phone, lat, lng"}` and nothing is changed.
- `description` only comes from the body (default empty). The suggestion's `note` was written for the admin and is never published.
- The fields are validated like a profile's (phone format, lengths, coordinate ranges). An unknown `category_id` is 400. An unknown suggestion is 404.

## Details settled during the backend build

- Validation errors (422) return one string in `detail`, not FastAPI's default list.
- `whatsapp` in responses falls back to `phone` when none was stored, so the app always has a number.
- Reviews, contact events and reports on a rejected (or unknown) profile return 404. Unverified and pending profiles can be reviewed and contacted like verified ones. Reviewing your own profile is 403.
- `DELETE /providers/{id}/reviews/mine` returns 204 even if there was no review.
- An unknown `category_id` is 400 on profile create or update, and an empty result in search.
- `category_id` in search includes direct children only (one level).
- Tokens must carry `aud: "authenticated"` (Supabase's default). A bad token on the public reviews list is treated as anonymous.
- "Today" (featured expiry) and the stats month are in UTC.
- `contacts_this_month` is the number of `whatsapp` + `call` contact events in the current UTC month (the same month as the stats); views are not included. It is `null` unless the provider turned on `show_contact_count`, also in `OwnProvider`. It is not part of search results. Counting itself is always on.
- Limits: name and area 100 characters, description and comment 2000, 10 photos, `author_name` required, up to 80.
- **Open decision:** `PATCH /me/provider` keeps the current `status` (apart from the proof rules above), so a verified provider can change name or category without a new review.
- `featured` in public shapes is `true` only for a verified provider whose `featured_until` has not passed. `OwnProvider.featured_until` shows the stored date whatever the status.
- Following needs a login but not a profile; a user may follow any public provider, including an unverified one or their own. `follower_count` counts every follower.
- The story limit (5 active) and the banner replace are done with the provider row locked, so two simultaneous posts cannot go over the limit.
- A listing with no owner (`claimed: false`) cannot be edited through `/me/provider`; claiming it is not built yet. The admin can still verify, reject or feature it.

## Rate limits

Write routes are limited per client IP, in the API process's memory (no extra service). Over the limit returns 429 with `{"detail": "..."}` and a `Retry-After` header.

- `POST /providers/{id}/contact-events`: 30 per minute per IP. In addition, the same IP, provider and type is counted at most once per 10 minutes; repeats still return 204 but are not stored. This keeps provider stats honest.
- `PUT /providers/{id}/reviews/mine`, `POST` and `PATCH /me/provider`, `POST /me/provider/stories`, `DELETE /me/provider/stories/{story_id}`, `PUT` and `DELETE /me/provider/banner`, `PUT` and `DELETE /providers/{id}/follow`: 20 per minute per IP. One shared allowance across these routes.
- `POST /suggestions`: 5 per hour per IP (its own allowance). Requests refused for a validation error count too.
- `POST /providers/{id}/reports`: 10 per hour per IP (its own allowance). Requests refused for a validation error or an unknown provider count too.
- `POST /assist`: `ASSIST_DAILY_LIMIT` (default 30) requests per IP per 24 hours that reach the AI. Exact name matches, remembered sentences and the `understood` form do not count. Over the limit the answer is HTTP 200 with kind `unavailable`, not 429, so the app simply falls back to a normal search.

Requests are counted before the login token is checked, so failed attempts use the allowance too. Behind a hosting proxy the client IP is read from `X-Forwarded-For`, counting `PROXY_HOPS` entries from the right so a client cannot fake it.

## Admin page

`GET /admin` (outside `/api/v1`) serves one static HTML page for the founder: enter the admin key, see profiles by status (Pending, Unverified, Verified, Rejected) with their proof link, approve, decline the proof, reject or restore, set founding member and featured-until. A "Suggestions" tab lists suggested providers with Publish (a small form for the fields that are still missing) and Delete. A "Reports" tab lists reported listings with Dismiss and Reject listing. A "Posts" tab lists active stories and banners with Delete (confirmed in the page, not with `window.confirm`). A "Wanted" tab shows `GET /admin/assist/wanted`: this month's assistant spending against the budget, the most asked unmatched requests and the place names that were not found. Each verified profile has Sponsor 7 / 30 / 90 days buttons (sets `featured_until` to today + N) and End sponsorship (sends `featured_until: null`); other statuses show a hint that only verified profiles count as sponsored. It only calls the admin endpoints above and the public `GET /categories`; the key is kept in the browser tab's memory, never stored.

## Photos and proof documents

The app uploads files straight to Supabase Storage using the user's login, then sends the resulting URLs to the API:

- bucket `provider-photos` (public read) for profile photos;
- bucket `verification-docs` (private) for proof.

Details (app side in `mobile/src/lib/upload.ts`):

- Each image is resized on the phone to 1600 px on its long side and saved as JPEG at quality 0.8 before upload.
- Path: `<auth.uid()>/<time>-<random>.jpg` in either bucket. Storage rules only let a signed-in user write, read, replace or delete inside the folder named after their own user id.
- `photos` holds the public URLs from `provider-photos`. The app sends at most 5 (the API allows 10).
- `verification_doc_url` holds a **signed URL** to the object in `verification-docs`, valid for one year, so the founder can open it from the admin page while the bucket stays private. The object path is visible inside the URL; after a year the founder can still open the file from the Supabase dashboard. The API accepts any text up to 1000 characters here; the admin page only links `http(s)` values.
- Buckets and rules are created by `supabase/storage_setup.sql` (run it once in the project's SQL editor). They do not exist on the hosted project until that file is run.
- No Supabase settings in the build: the app says photo upload is not set up and the listing can be sent without photos. Mock mode (no `EXPO_PUBLIC_API_URL`): uploads return placeholder `https://` links.

## Links the app builds itself

- WhatsApp: `https://wa.me/<number without +>?text=<prefilled greeting>`
- Call: `tel:<number>`
- Share: `https://haddak.app/p/<slug>` (domain not registered yet; the QR code encodes this link)
- Opening a share code inside the app: `haddak://p/<slug>` (the app's `scheme`) looks the code up with `GET /providers/by-slug/{slug}` and opens the profile. The https link will open the app the same way once the domain and Android app links exist.
