# Haddak — API contract

The contract between the mobile app and the FastAPI backend. Both sides are built against this file. Change it here first, then change the code.

- Base path: `/api/v1`
- JSON in and out, `snake_case` field names.
- Errors: `{"detail": "human-readable message"}` with a fitting status code (400, 401, 403, 404, 409, 422). Also when something fails on the server: **503** when the database is unreachable, busy (no free connection within 5 s), too slow (a query over 8 s) or read-only, so the app may try a GET again; **500** for any other unexpected error. Never a plain-text error page.
- Every response has an `X-Request-ID` header. The app may send its own (1 to 64 letters, digits, `-` or `_`), which is then returned unchanged; otherwise the server makes one. It is in the server's log line for that request and on the crash report, so a problem a user reports can be found.
- Interactive docs are generated by FastAPI at `/docs`.

## Authentication

Supabase Auth issues the login token. The app sends it as `Authorization: Bearer <access_token>`. The backend verifies the token's signature and reads the user id from the `sub` claim. The token header's `alg` picks the check: ES256/RS256 tokens (real Supabase sign-ins) are verified with the public keys from `SUPABASE_JWKS_URL`, with audience `authenticated`, `exp` required, and `iss` required to equal the project's issuer (`SUPABASE_JWKS_URL` without `/.well-known/jwks.json`, i.e. `https://<project>.supabase.co/auth/v1`). Clock leeway is 30 seconds. Tokens of Supabase "anonymous" users (`is_anonymous: true`) get 401. The keys are downloaded at most once an hour (5 s timeout); if a download fails, the keys already held stay in use and the next try waits 30 s. If no usable keys can be had at all, routes that need a login answer **503** `{"detail": "Sign-in check unavailable, try again"}` with `Retry-After` (never 401, so the app does not sign the user out), and public routes treat the caller as anonymous. Rejected tokens are logged by error type only, never the token. HS256 development tokens (`scripts/dev_token.py`, signed with `SUPABASE_JWT_SECRET`) are accepted only when `ALLOW_DEV_TOKENS=true`, which is never allowed in production. `alg: none` and any other algorithm get 401.

The app signs in with Supabase's email sign-in (PKCE flow). Email links open in a browser, which shows an empty page for an app link, so the email points to the backend page `GET /auth/open?app=<app link>` (outside `/api/v1`). The server checks `app` and writes it into the page: in production only `haddak://auth-callback` is accepted (an `exp://` link can point to any server, so it would hand the code to whoever runs that Expo project); in development also `exp://<ip>:8081/--/auth-callback` (Expo Go). A missing, repeated or refused `app` gives the same page with status 400 and no redirect. The page passes on **only** `code`, `error`, `error_code` and `error_description` (from the query, or else from the `#fragment`), as query parameters; never the rest of the address and never the fragment itself, so login tokens cannot be slipped through it. Allowed redirect URLs in the production Supabase project: `haddak://auth-callback` and `https://<api>/auth/open**` only (no `exp://**`, no LAN addresses; see `DEPLOY.md`). A local or development Supabase project may also list `exp://**` and `http://192.168.*.*:8000/auth/open**`. The app's `auth-callback` route exchanges the `code` for a session. It reads only the `code` and Supabase's `error_code` / `error_description` (from the query or the `#fragment`); a link that carries `access_token` / `refresh_token` is ignored, and a link opened while someone is already signed in is ignored too, so a link can never switch the phone to another account. If the email shows a 6-digit code instead (custom email templates, later), the user types it on the sign-in screen.

"Auth" below means the header is required; a missing or invalid token gives 401.

Admin routes use the header `X-Admin-Key: <ADMIN_API_KEY>` instead.

## Provider statuses and who sees what

A provider can be listed without being verified.

| Status | Public? | Meaning |
|---|---|---|
| `unverified` | yes, `verified: false` | No proof submitted, or the proof was not accepted. |
| `pending` | yes, `verified: false` | Proof submitted, waiting for the founder. |
| `verified` | yes, `verified: true` | The founder checked the proof. This is the badge. |
| `rejected` | no, 404 everywhere public | Fake, abusive or duplicate. |

- Public shapes never contain `status` or `verification_doc_url`. `pending` and `unverified` look identical to the public.
- Search returns verified providers only, unless `include_unverified=true` is sent. The API default stays `false`, but the app sends `true` by default (founder decision 2026-11-17: show everyone, verified first) and the assistant always searches with unverified included. Verified providers always come first.
- Verification is a human decision made in the admin page.
- Listings imported from OpenStreetMap (`source: "osm"`, see `SCHEMA.md`) are `unverified` and unclaimed, carry `data_source: "osm"`, and are shown with "Data © OpenStreetMap contributors".

| `GET /categories` | All categories, ordered by `sort_order`. Flat list; the app builds the tree from `parent_id`. Each item: `id`, `slug`, `name_en`, `name_ar`, `icon`, `parent_id`, `sort_order`, and `aliases` (list of extra search words, 2026-11-24) so the "All categories" screen can filter instantly on the phone. Sent with `Cache-Control: public, max-age=3600`: categories change only with a deploy, so the phone may keep the list for an hour. |
| `GET /providers/search` | Radius search. See below. |

`GET /providers/{id}` and `GET /providers/by-slug/{slug}` read the login token when one is sent, only to fill `is_following`. A missing or bad token is treated as anonymous.

### `GET /providers/search`

| Query | Type | Rules |
|---|---|---|
| `lat`, `lng` | float | required |
| `radius_m` | int | required, 100 to 50000. App chips: 500, 1000, 5000, 20000 ("city") |
| `category_id` | int | optional (1 to 2147483647, else 422); includes child categories |
| `q` | string | optional, 2 to 60 characters. Keeps providers where **any** of these match (all compared after `normalize_name()`, so Arabic letter forms, case and accents don't matter): the provider's name contains `q`; or the provider's category or its parent matches `q` (its `name_en`, `name_ar` or one of its `aliases` contains `q`, or is similar to it with pg_trgm `similarity() >= 0.4`, so "sankari", "سنكري" and "plumbr" find plumbers); or `area_name` contains `q`. Works together with `category_id` (both must hold). Providers whose name matches come first (see the order below). |
| `include_unverified` | bool | default `false`: verified providers only. `true`: also `unverified` and `pending` ones (never `rejected`). |
| `max_price` | number | optional (> 0); keeps only providers with a structured price `price_amount <= max_price`. Needs `price_unit`; `price_currency` defaults to `USD`. Providers without a structured price are left out when this is set. |
| `price_unit` | string | `hour`, `visit`, `job`, `item`, `month`; required with `max_price` (422 without it), ignored without it |
| `price_currency` | string | `USD` (default) or `LBP` |
| `open_now` | bool | default `false`; `true` keeps providers whose opening hours say open now (Beirut time), and also providers marked "Available now" (with or without hours). Other providers with no hours are left out. |
| `available_now` | bool | default `false`; `true` keeps only providers marked "Available now" (`available_until` in the future). |
| `sort` | string | `best` (default, the order below) or `distance` (nearest first; with `q` name matches still first, verified before non-verified, and among non-verified those with a phone first) or `price` (cheapest structured price first, then the default order) |
| `limit` | int | default 20, max 100. The app pages 20 at a time (`offset` 0, 20, 40…) and asks for up to 100 for the map. |
| `offset` | int | default 0, max 10000 (422 above) |

Response: `{"items": [ProviderSummary], "total": n}`. `total` counts every match, so the app can show "Showing 20 of 1,240" and knows when to stop loading. Order (`sort=best`): with `q`, providers whose **name** matches come first; then all verified providers before all non-verified ones; among non-verified ones, those with a phone or WhatsApp before those without; inside each group featured first, then weighted rating, then distance (see `SCHEMA.md`). Featured placement only counts for verified providers. `sort=price` compares the amount only (providers without a structured price last), so it is most useful together with `max_price`, which fixes the unit and currency.

### `POST /assist` (assistant, see `AI_ASSISTANT.md`)

No login needed. Free AI allowance per day (Lebanon time), counted only for requests that reach the AI: `ASSIST_DAILY_LIMIT_SIGNED_IN` (default 30) per account, or `ASSIST_DAILY_LIMIT_ANONYMOUS` (default 15) per phone when signed out, **and** `ASSIST_DAILY_LIMIT_PER_IP` (default 100) for everyone on one IP address. Over it, the free keyword fallback answers (never an error). The phone is identified by the optional header `X-Haddak-Device`: a random install id (UUID) the app makes once and stores; anything that is not a UUID is ignored. The account comes from the optional `Authorization` token. Without either, only the IP allowance applies.

Request, either a sentence:

```json
{ "text": "baddé sankari 2arib", "lat": 33.85, "lng": 35.52, "lang": "ar" }
```

or a chosen clarify option (no AI request is made; the settings are searched directly):

```json
{ "understood": { ...Understood... }, "lat": 33.85, "lng": 35.52, "lang": "ar" }
```

`text` 2–300 characters. `lang` (`ar` or `en`, default `en`) picks the language of `summary`. Send exactly one of `text` and `understood` (both or neither is 422). `lat` and `lng` are required.

In the `understood` form every field is optional (defaults: no categories, `radius_m` 1000, `price_currency` `USD`, `open_now` false, `sort` `best`) and is checked again like the AI's answer. `place` is read by its slug only: `{"slug": "jdeideh-metn"}` is enough, and anything else in it (names, coordinates) is ignored. This is what the app sends after the user taps one of `place_options`. A known slug centres the search on that place; an unknown slug is answered like a place we could not find (`place_unknown` = the slug, search near the phone).

`Understood` (what the AI returns, after the backend checks it):

```json
{
  "category_slugs": ["plumber"],            // only slugs that exist; may be empty when q is set
  "q": null,                                // optional name keyword
  "place": null,                            // or {"slug","name_en","name_ar","lat","lng"} after the lookup
  "radius_m": 1000,                         // 500, 1000, 5000 or 20000
  "max_price": null, "price_unit": null, "price_currency": "USD",
  "open_now": false,
  "sort": "best"                            // best | distance | price
}
```

Response:

```json
{
  "kind": "results",        // results | clarify | emergency | off_topic | unavailable
  "understood": { ... } | null,
  "summary": "Plumber · near you · 1 km",   // built from a template, not by the AI
  "results": { "items": [ProviderSummary], "total": 4 } | null,
  "widened": false,         // true when nothing was found and the radius was widened once (1 km → 5 km → 20 km)
  "question": null,         // clarify: {"text": "...", "options": [{"label": "...", "understood": {...}}]}
  "place_options": null,    // two places share the name: [{"slug","name_en","name_ar","district"}]
  "place_unknown": null,    // the place name we could not find; the search used the phone location
  "whatsapp_draft": "مرحبا، لقيتك على حدّك. عندي تسريب مي…" | null
}
```

- `unavailable`: the AI could not be asked (no API key, the monthly or daily spending cap reached, the daily AI allowance used up, or the AI failed) **and** the free keyword fallback found no category in the text. When the fallback does find one, the answer is a normal `results` (with `whatsapp_draft` null). On `unavailable` the app runs a normal name search with the text.
- `emergency`: the app shows its own built-in emergency numbers. `off_topic`: the app shows one fixed polite line.
- The AI request is sent only the sentence and the category list. The phone location never leaves the backend.

Details settled in the backend build:

- `summary` is always a string. For `results` it is the template (category, or the name keyword in quotes · `near you` or `in <place>` · radius · price limit · `open now` · `nearest first` / `cheapest first`, in English or Arabic); for the other kinds a fixed sentence.
- `results`: up to 20 items; `total` counts all. Unverified providers are included, always after every verified one. `distance_m` is measured from the search centre (the place when one was found, otherwise the phone).
- `understood.radius_m` is the radius finally searched. A found place sets it to at least the place's size (Jounieh: 5 km, Hamra: 1 km). Widening: when nothing is found, the next bigger radius is tried (500 → 1000 → 5000 → 20000) until something is found or 20 km was tried; `widened` is then true.
- When no category fits and no name keyword was given, `results` is `{"items": [], "total": 0}` without searching (and the request goes on the founder's "wanted" list).
- `clarify`: `understood` and `results` are `null`; `question.options` has 2 to 4 options, each with a full `understood` whose place (if any) is already looked up. `whatsapp_draft` may be set. The app sends the chosen option's `understood` back.
- `place_options` comes with kind `results`: the search ran near the phone, `understood.place` is `null`, and each option is `{"slug","name_en","name_ar","district"}`. Tapping one sends the `understood` form with `place: {"slug": ...}` (see above).
- `emergency`, `off_topic` and `unavailable`: only `kind` and `summary` are set; everything else is `null` (`widened` false).
- Unknown category slugs from the AI are dropped; at most 3 are kept. `radius_m` is snapped to the nearest of 500, 1000, 5000, 20000. A price limit without a unit is dropped; the currency defaults to `USD`.

### `POST /providers/{id}/reports`

```jsonc
{ "reason": "not_real", "note": "This shop closed years ago." }
```

`reason` is required: one of `wrong_info`, `not_real`, `closed`, `offensive`, `remove_my_business`, `other`. `remove_my_business` is "This is my business and I want it removed": the removal path for listings added without the owner's consent (OpenStreetMap imports, suggestions). The founder handles it with Reject listing in the admin page. `note` is optional, up to 500 characters. Nothing about the sender is stored (no user id, no IP).

### `POST /providers/{id}/claim` ("Is this your business? Claim it")

Auth. Body (both optional):

```jsonc
{ "message": "I am the pharmacist here.", "verification_doc_url": "https://…" }
```

- Only for a public listing with no owner (`claimed: false`); a claimed listing is 409, an unknown or rejected one 404.
- `message` up to 500 characters; `verification_doc_url` up to 1000 (a signed link from `verification-docs`, like profile proof).
- 409 when the user already owns a profile (one profile per user), or already has a `pending` claim for this listing.
- Returns 201 `Claim` with `status: "pending"`. The founder decides in the admin page. After approval the listing is the user's profile: `GET /me/provider` returns it and the app shows it in My business.

### `POST /suggestions`

Body (only `name` is required):

```jsonc
{ "name": "Abu Ali Tailor", "phone": "+96170123456", "category_id": 3,
  "area_name": "Mazraa", "note": "Best tailor in the area.",
  "lat": 33.8872, "lng": 35.4955 }
```

Limits: `name` 1 to 100 characters, `area_name` up to 100, `note` up to 500; `phone` in the same international format as provider phones. `lat` (-90 to 90) and `lng` (-180 to 180) are optional, but must be sent together: one without the other is 422. An unknown `category_id` is 400. Nothing about the sender is stored (no user id, no IP).

| `GET /me/feed` | `{"items": [StoryGroup]}`: active stories of the verified providers I follow, grouped by provider; newest story first; at most 30 providers. `distance_m` is null. |
| `GET /me/hire-checks/pending` | `{"items": [HireCheck]}`: my unanswered hire checks made 12 hours to 14 days ago, newest first, at most 3. Rejected providers are left out. |
| `POST /me/hire-checks/{id}` | Answer one. Body `{"answer": "hired" \| "not_yet" \| "no_answer"}`. 204. 404 if it is not mine or does not exist; 409 if already answered. |
| `POST /providers/{id}/claim` | Claim a listing nobody owns. See above. Returns 201 `Claim`. |

Create body:

```jsonc
{ "name": "Ali Tech", "category_id": 3, "description": "…", "price_text": "From $10",
  "price_amount": 10, "price_unit": "job", "price_currency": "USD",
  "phone": "+96170123456", "whatsapp": null,
  "lat": 33.8551, "lng": 35.5102, "area_name": "Haret Hreik",
  "photos": ["https://..."], "verification_doc_url": "…" }
```

Phone numbers must be in international format (`+` and 8 to 15 digits).

`verification_doc_url` is optional. How `PATCH /me/provider` treats it:

- On an `unverified` profile, sending a `verification_doc_url` that is not the one already stored moves it to `pending` (proof waiting for the founder). Sending the same URL again changes nothing, so a declined proof is not queued again by an ordinary edit.
- On a `pending` profile, clearing it with `null` moves the profile back to `unverified`.
- Every other edit keeps the status. A `verified` profile stays verified; a `rejected` profile stays rejected whatever is sent.

Two optional fields can also be sent on create and on update:

- `show_contact_count` (boolean, default `false`): when `true`, the public profile shows `contacts_this_month`.
- `opening_hours` (object or `null`, default `null`): see below. `PATCH` with `null` clears the hours.

- `price_amount` (number > 0, up to 100,000,000, or `null`), `price_unit` (`hour`, `visit`, `job`, `item`, `month`, or `null`) and `price_currency` (`USD` or `LBP`, default `USD`): the structured price that search filters and sorts on. `price_text` stays the free-text description. Amount and unit are set together or both `null`; one without the other is 422, also on `PATCH`, where the check is made against the stored values (sending only a new `price_amount` keeps the stored unit; clearing needs both set to `null`). `price_currency` cannot be `null`.

- `sponsor_hook` (string or `null`, default `null`): a one-sentence pitch, 1 to 80 characters. `null` (or an empty string) clears it. The owner may set it at any time, but the public only receives it while the profile is sponsored (see "Sponsored" below).

### "Did you hire them?"

When a signed-in user taps WhatsApp or Call, the app sends the contact event with the login token and the backend stores a hire check. From 12 hours later the app asks once: "Did you hire them?" (Yes / Not yet / They didn't answer). Rules:

- At most one check per user and provider in 7 days: a new tap within 7 days of the last check (answered or not) creates nothing. A tap on your own profile creates nothing. The 10-minute contact-event de-duplication does not affect checks.
- After 14 days an unanswered check is no longer offered. It stays in the table.
- `hired` marks that user's review of the provider (now or written later) with `hired_through_haddak: true`, and counts in the provider's `confirmed_hires` for 90 days.
- `not_yet` is just recorded. `no_answer` is counted for the founder only (`no_answer_count_90d` in the admin provider list); the public and the owner never see it.
- Search ranking does not use any of this yet.

### Stories and banners

Only the owner of a `verified` profile may post: 404 without a profile, 403 while the profile is not verified. Deleting your own story or banner is always allowed.

- **Story.** `text` 1 to 280 characters; `image_url` optional (`null` or an empty string means none), must start with `https://`, up to 1000 characters. It is active for 24 hours (`expires_at` = `created_at` + 24 h). At most 5 active stories per provider: a sixth is 409 until one expires or is deleted.
- **Banner.** One per provider; `PUT` replaces the old one. Body:

```jsonc
{ "title": "Back to school offer", "text": "All laptop repairs this week.",
  "discount_percent": 20, "days": 7 }
```

`title` 1 to 60 characters. `text` optional, up to 200 (`null` or an empty string means none). `discount_percent` optional, 1 to 90. `days` optional, 1 to 7, default 7: the banner starts now (`starts_at`) and expires `days` days later.

Expired stories and banners are simply no longer returned; nothing deletes them in the background. If a profile stops being verified, its stories and banner are hidden everywhere public until it is verified again: `has_active_story` is `false`, `banner_title` and `active_banner` are `null`, and its story list is empty.

### Sponsored

"Sponsored" is what users see for the admin's "featured" placement. `sponsored` is `true` when the provider is verified and `featured_until` has not passed; it always equals `featured`, which is kept for older app builds. `sponsor_hook` is `null` unless `sponsored` is `true`. Sponsored providers come first among verified ones in search (the existing featured rule; nothing else about the order changed). There are no payments in the app: the admin sets `featured_until` by hand.

### Available now

For providers without fixed hours (a plumber who works when called). The owner switches it on from My business for 2, 4 or 8 hours; it turns itself off when `available_until` passes, so a forgotten switch never stays on for long. `available_now` in `ProviderSummary` is `true` while `available_until` is in the future. Nothing runs in the background: the time is compared on every read. Search does not rank by it; the `available_now` filter, the widened `open_now` filter and the assistant's urgent words (see `AI_ASSISTANT.md`) use it.

### Opening hours

```jsonc
{ "mon": [["09:00", "13:00"], ["15:00", "19:00"]], "sat": [["10:00", "14:00"]] }
```

- Keys: any of `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun`. Any other key is 422.
- Each day: a list of at most 3 `[open, close]` pairs, 24-hour `"HH:MM"` from `00:00` to `23:59`, with open before close.
- A missing day (or an empty list) means closed that day. `null` for the whole field means "hours not provided".
- No overnight ranges in v1: a range cannot cross midnight (`["22:00", "02:00"]` is 422). `["00:00", "23:59"]` is the longest possible day.
- Times are Lebanon local time. `open_now` is computed in the `Asia/Beirut` timezone: open from the opening minute up to, but not including, the closing minute. It is `null` when `opening_hours` is `null`.

### Status changes (`PATCH /admin/providers/{id}`)

The admin page's buttons all send `status` to this one route:

| Action | Body | Used on |
|---|---|---|
| Verify (Approve) | `{"status": "verified"}` | `pending` or `unverified` |
| Decline proof | `{"status": "unverified"}` | `pending`. The listing stays visible, without the badge. The proof link is kept so the founder can still see what was declined. |
| Reject | `{"status": "rejected"}` | any. Hidden everywhere public. |
| Restore | `{"status": "unverified"}` | `rejected`. Listed again, without the badge. |

The route accepts any of the four statuses and does not check which status the profile had before: the admin is trusted.

### `POST /admin/suggestions/{id}/publish`

Creates a provider with `status: "unverified"`, `source: "suggestion"` and no owner (`claimed: false`), with a share code generated like any other profile's. The suggestion is deleted in the same transaction.

The body is optional. Any field in it overrides the suggestion's value; a field left out or `null` keeps the suggestion's value:

```jsonc
{ "name": "Abu Ali Tailor", "phone": "+96170123456", "category_id": 3,
  "area_name": "Mazraa", "lat": 33.8872, "lng": 35.4955, "description": "…" }
```

- After merging, `name`, `phone`, `category_id`, `area_name`, `lat` and `lng` must all be present; otherwise 422 with `{"detail": "Missing: phone, lat, lng"}` and nothing is changed.
- `description` only comes from the body (default empty). The suggestion's `note` was written for the admin and is never published.
- The fields are validated like a profile's (phone format, lengths, coordinate ranges). An unknown `category_id` is 400. An unknown suggestion is 404.

### `POST /admin/claims/{id}/approve`

In one transaction:

- 409 unless the claim is `pending`, 409 if the listing has an owner by now, 409 if the claimer owns another profile meanwhile. Nothing changes then.
- `owner_user_id` becomes the claimer. `source` stays as it was (an OpenStreetMap listing keeps its attribution).
- With proof (`verification_doc_url` on the claim), the proof is copied to the listing and the owner's proof rule applies: an `unverified` listing becomes `pending` and waits in the normal verification queue; `pending` and `verified` stay as they are. Without proof the status does not change.
- The claim becomes `approved` and every other `pending` claim for that listing becomes `rejected`. `decided_at` is set.

## Details settled during the backend build

- Validation errors (422) return one string in `detail`, not FastAPI's default list.
- `whatsapp` in responses falls back to `phone` when none was stored, so the app always has a number.
- Reviews, contact events and reports on a rejected (or unknown) profile return 404. Unverified and pending profiles can be reviewed and contacted like verified ones. Reviewing your own profile is 403.
- `DELETE /providers/{id}/reviews/mine` returns 204 even if there was no review.
- An unknown `category_id` is 400 on profile create or update, and an empty result in search.
- `category_id` in search includes direct children only (one level).
- Tokens must carry `aud: "authenticated"` (Supabase's default). A bad token on the public reviews list is treated as anonymous.
- "Today" (featured expiry) and the stats month are in UTC.
- `contacts_this_month` is the number of `whatsapp` + `call` taps **by signed-in users** in the current UTC month (the same month as the stats), at most one per user per provider per UTC day; views are not included. Anonymous taps (anyone can send them from a script) count only in the owner's private stats. Taps stored before 2026-11-25 keep counting. It is `null` unless the provider turned on `show_contact_count`, also in `OwnProvider`. It is not part of search results. Counting itself is always on.
- Limits: name and area 100 characters, description and comment 2000, 10 photos, `author_name` required, up to 80.
- **Open decision:** `PATCH /me/provider` keeps the current `status` (apart from the proof rules above), so a verified provider can change name or category without a new review.
- `featured` in public shapes is `true` only for a verified provider whose `featured_until` has not passed. `OwnProvider.featured_until` shows the stored date whatever the status.
- Following needs a login but not a profile; a user may follow any public provider, including an unverified one or their own. `follower_count` counts every follower.
- The story limit (5 active) and the banner replace are done with the provider row locked, so two simultaneous posts cannot go over the limit.
- A listing with no owner (`claimed: false`) cannot be edited through `/me/provider` until a claim for it is approved (`POST /providers/{id}/claim`). The admin can still verify, reject or feature it.

## Rate limits

Limits are kept in the API process's memory (no extra service). Over the limit returns 429 with `{"detail": "..."}` and a `Retry-After` header.

Each limit below is **per caller**: per user id when a valid login token is sent, otherwise per IP address. An IPv6 address counts by its /64 network (one home or phone gets a whole /64). A signed-in caller's IP is also counted against a **backstop of 10 times the limit** (for example 200 writes per minute per IP), so many phones behind one carrier address (Alfa and Touch use carrier-grade NAT) do not share one allowance, while one machine with many accounts still cannot send without limit. Anonymous callers behind one carrier address do share the per-IP limit; if 429s on reads show up in the logs at launch, raise the read limits first.

- `POST /providers/{id}/contact-events`: 30 per minute per caller. In addition, the same caller (user id, or IP when anonymous), provider and type is stored at most once per 10 minutes; repeats still return 204 but are not stored. This rule is kept in the database (table `contact_event_dedup`), so it survives restarts.
- `PUT /providers/{id}/reviews/mine`, `POST` and `PATCH /me/provider`, `PUT` and `DELETE /me/provider/available`, `POST /me/provider/stories`, `DELETE /me/provider/stories/{story_id}`, `PUT` and `DELETE /me/provider/banner`, `PUT` and `DELETE /providers/{id}/follow`, `POST /me/hire-checks/{id}`, `DELETE /me`: 20 per minute per caller. One shared allowance across these routes. (`DELETE /providers/{id}/reviews/mine` is not limited.)
- `POST /suggestions`: 5 per hour per caller (its own allowance). Requests refused for a validation error count too.
- `POST /providers/{id}/reports`: 10 per hour per caller (its own allowance). Requests refused for a validation error or an unknown provider count too.
- `POST /providers/{id}/claim`: 5 per hour per caller (its own allowance).
- `GET /providers/search` and `GET /stories/nearby`: 120 per minute per caller (one shared allowance; these are the costly queries).
- `GET /providers/{id}`, `GET /providers/by-slug/{slug}`, `GET /providers/{id}/reviews`, `GET /providers/{id}/stories`, `GET /categories`: 300 per minute per caller (one shared allowance).
- `POST /assist`: 20 requests per minute per caller, all requests (429 over it). Separately, the free daily AI allowance described under `POST /assist`, kept in the database (table `assist_quota`) so it survives restarts. Exact name matches, remembered sentences and the `understood` form do not count. Over the allowance the free keyword fallback answers instead (HTTP 200, kind `results`, or `unavailable` when it finds no category), never 429.
- Every route: a request body over 64 KB gets 413 `{"detail": "Request body is too large."}`.

Requests are counted before the route's own checks, so failed attempts use the allowance too (a missing or bad token counts as anonymous, by IP). Behind a hosting proxy the client IP is read from `X-Forwarded-For`, counting `PROXY_HOPS` entries from the right so a client cannot fake it. Once per start the API logs how many entries that header carries (a count, never addresses), so `PROXY_HOPS` can be checked.

## Photos and proof documents

The app uploads files straight to Supabase Storage using the user's login, then sends the resulting URLs to the API:

- bucket `provider-photos` (public read) for profile photos;
- bucket `verification-docs` (private) for proof.

Details (app side in `mobile/src/lib/upload.ts`):

- Each image is resized on the phone to 1600 px on its long side and saved as JPEG at quality 0.8 before upload.
- Path: `<auth.uid()>/<time>-<random>.jpg` in either bucket. Storage rules only let a signed-in user write, read, replace or delete inside the folder named after their own user id.
- `photos` holds the public URLs from `provider-photos`. The app sends at most 5 (the API allows 10).
- `verification_doc_url` holds a **signed URL** to the object in `verification-docs`, valid for one year, so the founder can open it from the admin page while the bucket stays private. The object path is visible inside the URL; after a year the founder can still open the file from the Supabase dashboard. The admin page only links `http(s)` values.
- The API checks where links point (2026-11-25), on `POST`/`PATCH /me/provider`, `POST /me/provider/stories` and `POST /providers/{id}/claim`, else 422: each photo and a story's `image_url` must start with `<SUPABASE_URL>/storage/v1/object/public/provider-photos/` and be at most 500 characters; `verification_doc_url` must start with `<SUPABASE_URL>/storage/v1/object/sign/verification-docs/` and be at most 1000 characters. No spaces, backslashes or `/../`. When `SUPABASE_URL` is empty (development and tests only; production refuses to start without it) any `https://` link is accepted. An empty `verification_doc_url` is treated as `null`.
- Storage caps each user at 100 files in `provider-photos` and 10 in `verification-docs` (`supabase/storage_setup.sql`).
- Buckets and rules are created by `supabase/storage_setup.sql` (run it once in the project's SQL editor). They do not exist on the hosted project until that file is run.
- No Supabase settings in the build: the app says photo upload is not set up and the listing can be sent without photos. Mock mode (no `EXPO_PUBLIC_API_URL`): uploads return placeholder `https://` links.
